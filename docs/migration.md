# Four-seed marketplace migration

## Status and scope

**Status:** planned, not executed.

This document sequences a future migration from the current two prototype dbt seeds to the four canonical CSVs generated by `plug-tech-screen`. The current change adds this runbook only. It does **not** copy seeds, change dbt configuration, modify SQL/YAML/tests, run a warehouse load, recreate relations, or authorize `--full-refresh`.

The migration is a coordinated, breaking graph cutover rather than a compatible file refresh. The two replacement files reuse existing filenames but have incompatible schemas and semantics; two additional sources are new. Existing staging targets and downstream models cannot safely coexist with a partial cutover.

### Non-goals

- Do not add a legacy compatibility layer, aliases, manifests, hash inventories, backup CSVs, staged bundles, or extra handoff files.
- Do not repair, normalize, deduplicate, reorder, or filter the raw CSVs in place.
- Do not copy generator code, author-only fixtures, expected dispositions, survivor maps, target identifiers, latent values, or expected lifecycle answers into this repository.
- Do not add packages, broaden the mart surface, or introduce production ingestion infrastructure as part of this fixture migration.

Common rules:

- The physical delivery key is `(source_system, source_record_id)`.
- `request_id` is the request/lifecycle grain.
- `synthetic_vin` is the authoritative cross-source vehicle trace key in this fictional dataset.
- Every source includes delivery, schema, source-update, and ingestion evidence.
- File order is parsed `ingested_at` instant, then `source_record_id`; business logic must not use file order as event order.
- The observation cutoff is exclusive: `2026-07-31T00:00:00Z`.
- Explicit timestamp offsets, exact decimal text, integer-cent amount representations, supported conditional nulls, and unsupported physical envelopes must survive the raw boundary as evidence.

At preflight, compare each complete ordered header directly with both the approved source CSV and `plug-tech-screen`'s executable schema. That comparison is stronger and less stale than duplicating all column names in this runbook.

### Why the cutover is breaking

The current seed schemas are prototypes:

- Current valuation rows use fields such as `vin_like`, submitter/account attributes, contact fields, postal code, and `channel`. The replacement uses `synthetic_vin`, `seller_id`, `submission_channel`, and `market_region`, and does not include contact fields.
- Current offer rows carry `offer_amount`, `offer_amount_unit`, and `currency_code` on the old event shape. The replacement uses a conditional pricing-evaluation block on pricing-bearing events; terminal events intentionally omit that block.
- Assessments and marketplace events have no current seed or staging interface.

Consequences in the current graph:

- `models/staging/stg_valuation_requests.sql/.yml` and `stg_offer_events.sql/.yml` select obsolete fields.
- Existing incremental staging targets contain prototype schemas and watermarks. `on_schema_change='append_new_columns'` cannot make an append safe.
- `models/core/fct_events.sql/.yml` implements an earlier two-source earliest-delivery view of business events, not the required source-specific disposition and canonicalization flow.
- Four analyses depend on removed fields or obsolete interpretations: `missing_offer_amounts.sql`, `non_dollar_offer_amount_units.sql`, `normalized_vin_like_collisions.sql`, and `valuation_requests_without_offers.sql`.
- `duplicate_offer_event_sequences.sql` and `duplicate_offer_source_event_ids.sql` still reference fields present in the target offer source, but they are diagnostics rather than sufficient replay-disposition logic.
- Existing reverse-completeness tests join only on `source_record_id`; the target physical namespace is composite.
- `assert_fct_events__duplicate_deliveries_agree.sql` follows the current fact's limited replay contract.
- `stg_example.sql` and `_staging.yml` do not satisfy the current same-base SQL/YAML and incremental-staging rules.
- `README.md` and the project-contract skill reference describe only the prototype interface.

### Phase 2 — static seed preflight

Before a warehouse load, use a deterministic, read-only profiler to verify each destination CSV:

- exact filename and full ordered header equality with the approved source and executable schema;
- expected data-row and column counts from the target inventory table;
- UTF-8 without BOM, LF-only line endings, one terminal LF, no blank lines, comma delimiter, and quote-all encoding;
- exact field count on every row and `""` as the missing-value representation;
- fixed source system and uniqueness of `(source_system, source_record_id)`;
- parseability of every required timestamp as an offset-aware instant;
- ascending parsed `ingested_at`, then `source_record_id` ordering;
- `ingested_at` strictly before the exclusive cutoff;
- null counts/rates, distinct counts, categorical frequencies, numeric/date/timestamp ranges, and relevant outliers for every column;
- source-specific conditional field presence; and
- cross-source request and vehicle relationships as evidence to be dispositioned, not silently repaired.

File-envelope violations block the load. Row-level business, schema-version, nullability, identity, temporal, or event-rule violations remain raw evidence and must reach physical staging for runtime disposition.

### Phase 3 — configure a text-preserving seed boundary

Update `dbt_project.yml` only after profiling the copied files:

- enumerate every column of each of the four seeds under an explicit per-seed `column_types` configuration using Snowflake `VARCHAR`;
- set `quote_columns: false` for these legal lower-snake-case identifiers;
- do not cast timestamps, amounts, versions, or identifiers at the seed boundary; and
- do not add a package dependency for this migration.

`quote_columns` governs relation identifiers, not CSV value quoting. Snowflake may expose unquoted column metadata in uppercase.

This configuration is the intended lossless boundary, not proof of losslessness. After the approved load, verify adapter behavior and stored values. In particular, confirm lexical versions, explicit offsets, decimal and integer-cent text, opaque identifiers, and quoted missing fields remain interpretable as the contract requires.

Run `dbt parse` and narrowly scoped `dbt ls` after configuration/model drafts and before warehouse mutation. Parsing does not validate the warehouse.

### Phase 4 — perform the approved four-seed load and profile Snowflake

Use only the exact command and selector approved at Gate 4. Load all four seed relations as one controlled deployment step; do not intentionally expose a two- or three-seed target interface.

Immediately profile each loaded seed relation in the confirmed development target:

- warehouse type for every column, requiring `VARCHAR`;
- row count and composite physical-key uniqueness;
- null count/rate and distinct count for every column;
- representative raw lexical values and quoted-empty-field behavior;
- raw and parsed timestamp values, offsets, parse failures, and min/max instants;
- categorical domains and frequencies;
- exact-decimal parsing, signed values, units, and currency fields;
- conditional field matrices by status or event type; and
- cross-source request, vehicle, and event relationships.

Use bounded, cost-conscious dbt queries. Stop if the load changes a required lexical distinction, a required timestamp cannot be parsed, the wrong target was selected, or observed data contradicts the contract.

### Phase 5 — create four physical-grain staging pairs

Future staging inventory:

| SQL/YAML pair | Action |
| --- | --- |
| `models/staging/stg_valuation_requests.sql/.yml` | Replace prototype contract |
| `models/staging/stg_vehicle_assessments.sql/.yml` | Add |
| `models/staging/stg_offer_events.sql/.yml` | Replace prototype contract |
| `models/staging/stg_marketplace_events.sql/.yml` | Add |

Recreate the two existing staging targets before running replacement SQL. Do not append the new contract to prototype tables or rely on `on_schema_change='append_new_columns'`.

Each staging SQL model must:

- explicitly use incremental append materialization;
- omit `unique_key`, merge logic, deduplication, repair, and lifecycle selection;
- retain every raw field and delivery-provenance value;
- derive a deterministic, non-null physical delivery key from a source-specific namespace, `source_system`, and `source_record_id`;
- preserve raw timestamp text and add explicitly typed, offset-aware instant derivatives;
- fail visibly if a required non-null ingestion timestamp cannot be parsed;
- use the parsed ingestion instant as the incremental watermark;
- load all rows when the target maximum watermark is null;
- otherwise append only rows whose parsed watermark is strictly greater than the target maximum;
- preserve conditional nulls rather than filling them with zeros or fallback values; and
- use exact fixed-precision numeric types for interpreted money and explicit tested normalization while retaining raw text.

Equal-watermark and earlier late arrivals remain evidence. The strict boundary may skip them on an incremental run; reverse completeness must expose that condition and force an explicitly approved rebuild decision.

Each paired YAML file must:

- use `version: 2` and name exactly the sibling SQL model;
- document purpose, physical grain, transformations, incremental boundary, raw/parsed fields, and non-obvious conditional null semantics;
- list every final-select column alphabetically;
- give every column a meaningful semantic description; and
- include at least one meaningful, contract-backed test per final-select column after profiling the loaded staging output.

Test selection order is native dbt generic test, then an already-supported generic test, then a singular SQL test when neither generic form expresses the invariant. Use `not_null` only for contract-required values, `unique` only for the physical delivery key, accepted domains only when frozen by the contract, and range tests only for defensible inclusive/exclusive bounds. Block completion rather than inventing a test when profiling and the contract do not establish a stable invariant.


### Phase 7 — derive disposition and canonical inputs at runtime

Approve exact model names and grains at Gate 5 rather than treating names in a planning document as contracts. Prefer source-specific models because immutable keys, replay comparison payloads, field matrices, and event rules differ by source.

The approved flow must derive from staged data:

```text
physical deliveries
    -> supported-version and row-contract checks
    -> replay grouping and complete payload comparison
    -> deterministic survivor selection
    -> cross-source identity, temporal, amount, and event validation
    -> accepted / duplicate / quarantined disposition
    -> canonical accepted survivors
```

Requirements:

- Emit exactly one disposition record per physical composite delivery key.
- Keep warnings and normalization flags separate from disposition.
- Use a composite survivor pointer or the staging delivery key; never use an unqualified `source_record_id` as a cross-source pointer.
- Compare timestamps by parsed instant while retaining raw representations.
- Select replay survivors deterministically under the source contract.
- Quarantine conflicting immutable-key groups rather than choosing an arbitrary winner.
- Preserve nonblocking quarantines without automatically discarding an otherwise defensible request path.
- Include enough source lineage to join every disposition back to physical staging.
- Feed canonical models with accepted survivors only.

Tests must prove:

```text
physical rows = accepted rows + duplicate rows + quarantined rows
```

Also prove dispositions are exhaustive and mutually exclusive, every physical row appears once, duplicate survivor pointers are valid, canonical inputs contain only accepted survivors, and no row is silently deleted or repaired. Derive these results at runtime; do not persist expected totals, target IDs, survivor maps, or author-oracle outputs.

## Partial failure and rollback

### Partial failure

The warehouse cutover is not assumed atomic. If any seed load, relation recreation, or required validation fails:

1. stop downstream execution;
2. prevent consumers and concurrent jobs from using the mixed graph;
3. record which relations changed and which checks completed;
4. choose either completion or rollback under the approved recovery procedure; and
5. do not describe the migration as complete until all four sources and the approved downstream graph pass.

### Rollback inventory

Git revert alone does not restore warehouse state or delete newly created relations. A complete rollback must:

1. revert the focused migration commit or restore the approved old file revision;
2. reload the old two seed relations under an approved command;
3. recreate the old `stg_valuation_requests`, `stg_offer_events`, and `fct_events` relations;
4. remove the added assessment and marketplace seed relations;
5. remove every new staging, disposition, canonical, and lifecycle relation created by the migration;
6. restore affected ownership and grants;
7. restore schedules or consumers only after the old graph validates; and
8. rerun scoped old-graph row-count, key, relationship, test, and consumer smoke checks.

Use a clone or Time Travel recovery path only after confirming privileges, retention, names, grants, and restoration steps before mutation.
